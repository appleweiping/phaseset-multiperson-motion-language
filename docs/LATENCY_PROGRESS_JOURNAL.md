# Durable latency progress journal

This optional journal preserves a diagnostic prefix when a latency session
fails or stops. It is POSIX-only; importing the module is portable, while
creating or reading a journal on an unsupported runtime fails explicitly.
Journal integration tests are correspondingly POSIX-scoped.

## Files and ordering

The controller exclusively creates a fresh session below trusted, stable
private ancestors. The writer uses mode 0700 for the session directory and
0600, exclusive no-follow creation for canonical event files. Events and
sequence markers are flushed and synchronized in a fixed order. Every event
binds its sequence, predecessor digest and the external cohort, scorer,
installed-source, protocol, wrapper and registered-device identities.

The typed interface allows only session start, context ready, visit start,
warmup completion, timed-sample completion, visit end and terminal events. It
does not offer arbitrary metric insertion. A successful fixed session has
1461 committed events. Enumeration stops at fixed bounds before collecting an
unbounded directory; event count, leaf count and individual byte sizes are
separately bounded. Reads require stable, single-link regular files.

These checks assume trusted stable ancestors and are not a sandbox against
hostile concurrent filesystem writers. Read-only flags and digests are not
operating-system immutability or external authorization.

## Failure semantics

The latency runner owns all actual visit/sample observations. Observer calls
occur after the corresponding operation; timed-sample callbacks run after the
timer has stopped. One callback failure latches observation failure, holds the
latency session and prevents later callbacks. Previously committed files are
never erased or rewritten to make the attempt appear successful.

A callback can finish durable terminal commit and then throw. The committed
terminal cannot be rolled back:

- After a COMPLETED terminal, the API can conservatively hold the session even
  though the reader sees a structurally complete, nonformal terminal. The
  complete-session digest differs from the subsequently held-session digest.
- After a HELD terminal, the API retains the original held receipt and chains
  the observer exception. The reader can retain that matching nonformal HELD
  terminal.

The controller must cross-check the actual API outcome, session receipt and
terminal digest. Neither terminal grants formal status on its own. An
incomplete committed prefix or one physically uncommitted tail is preserved;
the reader does not infer whether a hard kill, interruption or I/O failure
caused it. `KeyboardInterrupt`, `SystemExit` and hard kills are not recast as
successful sessions.

## Observed scope

The journal dependency passed a 68-test Linux suite in 14.13 s with source
unchanged. A previous attempt passed its software assertions but failed its
source-stability check because an isolated SIGKILL child generated bytecode.
That attempt remains failed. Adding explicit `-B` to that test child fixed the
harness without deleting the original files or weakening the comparison.

The final latency-to-journal integration passed 73 combined tests in 22.63 s.
It includes all 81 fake-runtime visits, real durable filesystem writes,
admission failure, active-visit failure, post-sample callback failure, and a
post-commit COMPLETED-terminal exception. Those fixtures establish software
mechanics, not real GPU timings or formal training. The merged 1211-test
server regression is reported in
[base qualification](BASE_COHORT_QUALIFICATION.md).
